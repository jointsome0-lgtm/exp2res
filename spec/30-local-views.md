## §30. Local Views

§30 specifies the local-view shape for selfos embedding. V1 ships the CLI first, and the view slice inside its scope is the mirror view plus the gap-question view that the §14.17 command serves on loopback. Like every other § of this document, that scope is a binding contract on the implementation rather than a report of one: the slice builds in §22's Phase 3, where §24.59 and §21.57 track it and stay `pending` until it does. The JD-to-bullet-pack view is not in V1 scope at all, and a complete resume document model remains a later post-mirror iteration under §18. That deferral does not relax the contracts below when the deferred view is built.

1. **Coupling and serving boundary.** A view is served only on a loopback local URL and is embedded only by that URL, configured outside Exp2Res. Exp2Res stores no consumer identity, shell schema, callback, webhook, or consumer-specific protocol. Serving the view is local presentation under §29.2, not egress, and grants no new network authority. The server binds exactly one literal loopback address, refuses any other requested bind before it serves anything, resolves no name, listens on no second interface, and opens no outbound connection of any kind. That bound address and port are the only authority it answers to, serialized exactly as `127.0.0.1:<port>` for the IPv4 bind or `[::1]:<port>` for the IPv6 bind: a request whose HTTP authority is any other value — including a name that currently resolves to loopback or an authority omitting the explicit port — is refused before any state is read, so an externally controlled name rebound onto the loopback address reaches nothing. A fetch-metadata site declaration is not consulted and never decides an outcome: the consumer this surface exists for is a shell that embeds the view by URL from its own web origin, so the browser sends `cross-site` or `same-site` on precisely the navigation §30 is built to serve, and refusing that declaration would refuse the intended embed. The declared-origin check below does not have that effect, because browsers omit `Origin` on the top-level and frame navigations embedding uses; it therefore refuses only a script-initiated cross-origin read, whose response the same-origin policy already keeps unreadable by the page that asked for it. An allowlisted shell origin is not the alternative either — it would be exactly the consumer-specific configuration this rule forbids. A request that declares any other origin is refused the same way, before state is read: a page elsewhere may still send a request carrying this authority, and refusing it is stricter than declining to grant it the read. Exp2Res establishes no session, cookie, credential, or consumer identity, and no response grants or sets one or a cross-origin read. Cookies are not port-scoped, so a browser may attach one another local service set for this host; such a header is ignored entirely — never read as identity, never stored, never logged — and grants nothing, because no route consults any request header except rule 6's closed set. The bound loopback socket is therefore the whole trust boundary: Exp2Res authenticates no local peer, so while the owner-initiated foreground command runs, any process that can reach that port on this host — including one running as another local account — can read exactly what the owner can, which the workspace's owner-only file modes would otherwise deny it. That is a deliberate V1 position for a single-operator local instance rather than an oversight: serving is explicitly started, ends with the command, and §29.6 records the exposure as a stated limit. A local-peer capability check is a named later addition, and no configured value may widen the bind in its place.

   The declared-origin representation is closed and literal. An absent `Origin` field passes this check. Otherwise the request must carry exactly one field with that ASCII-case-insensitive name; repetition, even with byte-equal values or different name casing, is `malformed_request` during transport parsing before the authority check. After HTTP optional whitespace is trimmed, only the exact ASCII bytes `http://127.0.0.1:<port>` for the IPv4 bind or `http://[::1]:<port>` for the IPv6 bind equal the bound origin. The value is never split, decoded, case-folded, default-port-filled, or otherwise normalized. Every other syntactically valid single field-value — including empty, `null`, a space-separated sequence, another scheme or authority, or one that omits the explicit port — is `authority_not_bound`; a header section invalid before that comparison remains `malformed_request` under rule 9.
2. **Read and action authority.** View rendering is read-only over selected current derived state. A user action may delegate only to an existing §14 flow with that flow's selectors, workspace lock, confirmation, exit class, and §14.14 result semantics; the view defines no new command, business mutation path, implicit latest selector, consent default, LLM call, or background work. A view-triggered provider call remains foreground and user-initiated under §29.2, and the view may not poll, queue, retry, resume, or complete it independently. The two V1-scope views take no action at all: they are read-only projections whose closed route set accepts exactly the methods `GET` and `HEAD`, carries no request body, and lets no path, query value, or header select a filesystem path, a command, a stage, or a business mutation. Every other method, `OPTIONS` included, is refused under rule 7 without resolving a selector. A `HEAD` request performs the same resolution and revalidation as the `GET` it mirrors and returns that outcome's status and headers with an empty body, so rule 6's body-equality requirement binds `GET` alone; an otherwise accepted `GET` or `HEAD` that declares a body is refused as malformed under rule 7's 400 outcome rather than read. An unsupported method remains `method_not_allowed` even when it declares a body, because rule 7 checks the method first. Because declared body bytes are never drained, either refusal closes the connection, so no undrained byte can be framed as the next request.

   Request framing has one closed classification, with the `Content-Length` and `Transfer-Encoding` field names recognized ASCII-case-insensitively. A request is bodyless only when both fields are absent or when it carries exactly one `Content-Length` whose value, after trimming HTTP optional whitespace, is the single ASCII digit `0`. Exactly one `Content-Length` whose trimmed value is a canonical positive decimal — `[1-9][0-9]*` — is a declared body, so it reaches the method-before-body order above without the server reading or integer-converting its bytes. Every other framing form is a transport parse failure before the method check: any `Transfer-Encoding` field, a combination of the two fields, repeated `Content-Length` fields even when their values agree, or a `Content-Length` value outside those two canonical forms. Thus no parser normalization, comma joining, numeric overflow behavior, or duplicate-field policy can change the outcome.
3. **Mirror view.** The mirror view presents the §17 report for one explicitly selected current `AssessmentSnapshot` as local HTML, preserving §16.11 status gates, uncertainty, contradictions, and source/generated-voice boundaries. The URL carries that selection explicitly in one of exactly two closed forms: the assessment-view identity — `scope`, plus its target for a project scope — or one exact `AssessmentSnapshot.id`. There is no default selector, no omitted-selector fallback, and no latest-of-several rule: an identity selector resolves only to the unique current snapshot of exactly that view, and both zero and more than one resolution are fail-closed outcomes rather than a choice. V1 serves the `global` identity; a project-scope selector is refused as the deferred slice it is rather than silently widened. That HTML is exactly §17's `report.html` member: the view performs §13.14's complete current-output revalidation for the selected snapshot — rule 5's standard, not merely matching-manifest validation — and serves those published bytes. It never renders a second version of the same projection, never re-renders around a failed revalidation, and never renders a partial claim set to work around a gate; a missing, stale, or invalidated set is a fail-closed outcome that names the §14.9 export the owner must run. Interactive provenance drill-down from claim to signal to fact to evidence is a named later iteration and is not part of the first mirror view.
4. **JD-to-bullet-pack view.** The view accepts owner-pasted vacancy text, writes the exact validated bytes to one owner-only operation-owned temporary file inside the workspace, requires that file to pass §29.4, supplies its path to the existing §14.10 JD-add operation, and removes it on completion under §29.6; a validation or cleanup failure is an operational failure and reports any residual path. The remaining generation, verification, and export work delegates to the same §14.10 flow without adding another business persistence or model contract. A successful export is one outcome; a refusal required by §18 or a §16.11 gate is an equally first-class completed `blocked` outcome under §14.14, with its reason and findings shown rather than replaced by an error page. An operational failure remains an operational failure and may not be relabeled as a semantic refusal.
5. **Gap-question handoff.** The sole outbound question-of-the-day source is the gap-question view over the same explicitly selected set. Exp2Res, never the shell, performs §13.14's complete current-output revalidation — not merely matching-manifest validation — validates the closed companion schema of that set's `out/assessment/<snapshot-id>/self_claims.json` from §13.12–§13.14, projects only `unknowns` entries with `answered = false`, and presents only their `question` values — §17's open-question set. No other companion field, and no gap ID, target, reason, priority, claim, or contradiction, reaches the page, so a question stays readable without becoming an answer link-back token. The shell embeds one URL: it reads no companion file, manifest, or workspace path, inherits no companion schema, cannot bypass revalidation, and never constructs a path from the scope target. A stale historical set, a set invalidated by a later gap answer, or a cleanup residual is never a handoff source. Exp2Res receives no consumer identity or answer callback. An answer returns only through ordinary diary/activity capture or import as a new `RawLog`; it carries no gap ID or link-back token, and §14.7's no-relink rule remains unchanged.
6. **Closed route set and per-request revalidation.** The served routes are exactly `/mirror` and `/questions`, each carrying rule 3's selection as exactly one query selector — `scope`, or `snapshot`. When the deferred project scope is implemented, `scope=project` takes its target in exactly one additional `project` parameter carrying the §14.9 canonical project label, and that pair is the whole of the identity form; V1 recognizes the shape only to refuse it as deferred. Any other path, an absent, unknown, repeated, combined, or malformed selector, and any additional parameter are refused rather than interpreted. Matching runs on one fixed representation, so identical request bytes always receive identical structural parsing and selector interpretation; their state-dependent rule 7 outcome may change when the required per-request reads observe different workspace state. Structure is matched literally and before any decoding: the path, the `?`, `&`, and `=` delimiters, and every parameter name are compared as the ASCII bytes received, so a percent-escape standing in a structural position — `/m%69rror`, `?%73cope=global` — is never decoded into a match and is refused as `route_not_found` or `invalid_selector`. Only a selector value is percent-decoded, exactly once, and the octets it yields are interpreted as UTF-8; a value carrying a malformed or truncated escape, or decoding to bytes that are not valid UTF-8, is `invalid_selector`. The decoded `snapshot` value is then valid only when it matches §13.14 rule 1's stored snapshot-ID grammar exactly — 1–128 lowercase ASCII bytes matching `^[a-z0-9][a-z0-9_-]{0,127}$` — before any lookup; an empty, overlength, uppercase, dot-segment, separator-bearing, or otherwise nonmatching value is `invalid_selector`, while a grammar-valid value that names no current row is `no_current_view`. No second decoding pass ever runs, so a double-encoded value decodes to a literal percent sequence that resolves to nothing rather than to some other selector. The only request headers any route consults are the ones those refusals need: the authority and declared origin rule 1 checks, and the framing headers rule 2 reads to detect a declared body. Every other header is ignored — never interpreted, stored, or logged.

   Every request is its own read-only boundary: it re-reads §12.14 compatibility and performs its state reads inside one §8.1 read transaction, takes no workspace writer lock, and carries no cached bytes, resolution, or validation verdict between requests, so state that changed since the previous request is observed rather than served from memory. That read transaction is not free of effect and is therefore bounded: it opens when the request begins resolving and closes when the response is composed, before any byte reaches the socket, so a slow or idle client cannot extend a SQLite reader by even one byte's wait. Its duration is the server's own resolution and revalidation work and nothing else; §8.1's concurrent-reader outcome is unchanged, so a destructive checkpoint racing a request in flight may still report `deletion_incomplete`. It reads the revalidated member bytes once, so the bytes it serves are the bytes it verified. The mirror response body is exactly that revalidated `report.html` member; the gap-question response is one document generated under §17's HTML escaping, self-containment, and inertness rules over rule 5's projection alone. Beyond those two projections a response carries only rule 7's own outcome vocabulary — the outcome class, the §14 remedy command where one exists, and renderer-owned literal text — and a diagnostic line carries only the outcome class and, when the request named one, the closed route; neither ever carries request bytes, a workspace or managed path, `raw_text`, another companion field, or any other stored value. Every response is uncacheable, typed, and terminal for its connection: each declares `Cache-Control: no-store`, the exact media type `text/html; charset=utf-8`, and `Connection: close`, which a `HEAD` response carries too. So a revisited URL is resolved again by Exp2Res rather than replayed from an intermediate or browser cache, and no refusal is stored as a page. A document already delivered stays in the tab that rendered it, and Exp2Res controls that copy no more than it controls an opened §17 file member. The guarantee is therefore bounded to a navigation that actually reaches the network: that one resolves against current state instead of replaying a stored response. A history traversal that revives an already-rendered document from a back/forward cache issues no request at all, so no response directive can reach it, and the page it shows is the earlier delivered copy rather than a served answer. No page reflects request bytes back to its requester: a rule 7 remedy command names an `AssessmentSnapshot.id` only after resolution proved it is a current stored row, so what the page prints is state Exp2Res read, never a value a request supplied, and a refused, unresolved, or malformed selector reaches no page.
7. **Closed outcome set.** Every complete request admitted to handling resolves to exactly one outcome before response emission, and every completed HTTP response makes that outcome owner-visible. Each outcome names its class, and names the §14 command that resolves it when one exists — the rows below whose remedy is a corrected request rather than a workspace operation name none, and none invents guidance to fill the space — and states nothing else about local state; a completed semantic refusal is never presented as an operational failure, and an operational failure is never relabeled as a refusal. A connection closed before one complete request is admitted — rule 10's overload close or §14.17's receive expiry — has no request to answer. §14.17's ordinary emit expiry or absolute interruption-drain expiry may truncate delivery after the outcome is composed; neither creates a second outcome, emits an alternate response, or relabels cancellation as `internal_error`, and every HTTP response that does complete still comes from exactly one row below.

   A request that matches more than one row still has exactly one answer, because the checks are ordered and the first refusal decides it: rule 9's transport-envelope bounds and transport parsing first, because a request Exp2Res cannot parse — its request line, its header section, or its framing — carries no authority, method, or route to check, and that failure is the outcome rather than a parser-owned response outside this table; then rule 1's authority check, then the method, then rule 2's declared-body check, then the route, then selector parsing — all of it before any state is read — then §12.14 compatibility, then selector resolution, then §16.11's gate, then the managed set's revalidation, and, for `/questions` alone, rule 5's companion-schema validation. So a snapshot that both fails the allowlist and has had its stale set invalidated is the completed 403 refusal, never the 409 one: the export that row would name is exactly what the gate forbids. Inside the gate the integrity half runs before the status half: §16.11 requires exactly one `narrative_summary` member claim whose text equals `AssessmentSnapshot.summary`, and requires the stored aggregate to equal a fresh reduction of the current claims. A snapshot failing either is `assessment_inconsistent` even when its stored status is allowlisted, because a stored aggregate that no longer reduces from its own claims is not a verdict the allowlist can be read against — the refusal names broken stored state, not a judgment about the owner's evidence.

   Each row's class value is the stable literal that names the outcome, and every response carries it in the `Exp2Res-View-Outcome` header — a service-owned constant, never a request value — so the class survives a bodyless `HEAD` and a `--quiet` invocation that suppresses §14.17's progress line. A refusal page states its class and remedy in the body as well; a served response states neither, because the mirror body is exactly the published `report.html` bytes and the question page is rule 5's projection alone.

8. **V1 read-only serving-process boundary.** The §14.17 process and its `/mirror` and `/questions` routes perform no business mutation, no managed-output publication or reconciliation, no §12.13 `processing_runs` or §12.15 `llm_calls` row, and no §15 call, so a served page never authorizes what its underlying §14 flow would require. This boundary does not redefine the deferred rule 4 action surface: that view may later delegate only through the existing §14 flows rule 2 names, and it cannot widen this read-only command. §14.17 owns the V1 command form, its bind controls, and its §14.14 envelope; §8.1 classifies that command read-only and owns its per-request transaction discipline.

These views add no LLM transmission field, so §29.3 does not widen. They expose no source payload, result, or action beyond the selected §17 projection, the validated unknown-question projection, and the same §14 flows available without a view.

9. **Bounded transport envelope.** The raw request envelope is bounded before parsing or decoding: the request line is at most 8192 octets including its terminating CRLF; the header section after it is at most 32768 octets including every field-line CRLF and the terminating empty line; and it contains at most 64 field lines. Counts are cumulative across fragmented socket reads, so splitting one line or section never resets a bound. The parser may read at most one octet beyond the applicable byte cap to establish overflow and never buffers more than that capped component plus the one deciding octet. The accepted request-line grammar is exactly method, one SP, an origin-form request target, one SP, and `HTTP/1.1`, followed by CRLF. Origin-form begins with `/` and carries only the path plus optional query consumed by rule 6; absolute-form, authority-form, asterisk-form, another HTTP version, extra whitespace, or any other target form is `malformed_request` before authority or method refusal and is never normalized into a route. The header section must contain exactly one syntactically valid `Host` field, recognizing that field name ASCII-case-insensitively and counting every spelling toward the same cardinality: absence or repetition is `malformed_request`, while its one parsed authority reaches rule 1 and is `authority_not_bound` unless it is exactly the bound address and port. Exceeding any bound or failing any request-envelope rule is `malformed_request`, closes the connection after that response, and performs no compatibility or business-state read. These limits are fixed service constants with no flag, environment, or configuration representation.

   The header grammar is exact. The request line, every field line, and the terminating empty line end in CRLF; a bare LF, bare CR, or line beginning with SP or HTAB is invalid, so obsolete folding is never unfolded. A field line is one or more ASCII `tchar` bytes, immediately followed by `:` with no intervening whitespace, then zero or more field-value bytes, then CRLF. `tchar` is an ASCII letter, digit, or one of `! # $ % & ' * + - . ^ _` `` ` `` `| ~`. A field value may contain only SP, HTAB, or visible ASCII `0x21`–`0x7e`; every other control byte, DEL, or byte `0x80`–`0xff` is invalid. Leading and trailing SP/HTAB remain HTTP optional whitespace for the specific rule 1/rule 2 comparisons that trim it; no other byte is normalized. An empty value is syntactically valid unless a consulted field's owning rule rejects it. Any violation is `malformed_request` during transport parsing before authority or method evaluation.

10. **Bounded connection admission.** At most 32 accepted connections are admitted into transport parsing or request handling at once. A slot is acquired immediately after `accept` and before the first request byte is read, remains held through response emission or connection close, and is then released. The server handles at most one request on a connection and rule 6 makes every response declare `Connection: close`, so no keep-alive or pipelined request re-enters handling through an existing slot. The listener requests a backlog of 32 and the service maintains no application-level pending-connection queue. When all 32 slots are occupied, a newly accepted socket is closed immediately without reading, buffering, parsing, or emitting an HTTP response, so it is not a complete request under rule 7 and reaches no state. No thread, task, parser buffer, or request worker is created before a slot exists. These are fixed service constants with no flag, environment, or configuration representation.
