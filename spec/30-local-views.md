## §30. Local Views

§30 specifies the local-view shape for selfos embedding. V1 ships the CLI first, and the view slice inside its scope is the mirror view plus the gap-question view that the §14.17 command serves on loopback. Like every other § of this document, that scope is a binding contract on the implementation rather than a report of one: the slice builds in §22's Phase 3, where §24.59 and §21.57 track it and stay `pending` until it does. The JD-to-bullet-pack view is not in V1 scope at all, and a complete resume document model remains a later post-mirror iteration under §18. That deferral does not relax the contracts below when the deferred view is built.

1. **Coupling and serving boundary.** A view is served only on a loopback local URL and is embedded only by that URL, configured outside Exp2Res. Exp2Res stores no consumer identity, shell schema, callback, webhook, or consumer-specific protocol. Serving the view is local presentation under §29.2, not egress, and grants no new network authority. The server binds exactly one literal loopback address, refuses any other requested bind before it serves anything, resolves no name, listens on no second interface, and opens no outbound connection of any kind. That bound address and port are the only authority it answers to: a request whose HTTP authority is any other value — including a name that currently resolves to loopback — is refused before any state is read, so an externally controlled name rebound onto the loopback address reaches nothing. A request whose fetch-metadata site declaration is present and is neither `same-origin` nor `none` is refused by that same authority check, in the same 421 outcome, before state is read — it closes the gap left by a cross-origin navigation that carries no origin header at all, and its absence is never itself a refusal, since older clients send no such declaration. A request that declares any other origin is refused the same way, before state is read: a page elsewhere may still send a request carrying this authority, and refusing it is stricter than declining to grant it the read. Exp2Res establishes no session, cookie, credential, or consumer identity, and no response grants or sets one or a cross-origin read. Cookies are not port-scoped, so a browser may attach one another local service set for this host; such a header is ignored entirely — never read as identity, never stored, never logged — and grants nothing, because no route consults any request header except rule 6's closed set. The bound loopback socket is therefore the whole trust boundary: Exp2Res authenticates no local peer, so while the owner-initiated foreground command runs, any process that can reach that port on this host — including one running as another local account — can read exactly what the owner can, which the workspace's owner-only file modes would otherwise deny it. That is a deliberate V1 position for a single-operator local instance rather than an oversight: serving is explicitly started, ends with the command, and §29.6 records the exposure as a stated limit. A local-peer capability check is a named later addition, and no configured value may widen the bind in its place.
2. **Read and action authority.** View rendering is read-only over selected current derived state. A user action may delegate only to an existing §14 flow with that flow's selectors, workspace lock, confirmation, exit class, and §14.14 result semantics; the view defines no new command, business mutation path, implicit latest selector, consent default, LLM call, or background work. A view-triggered provider call remains foreground and user-initiated under §29.2, and the view may not poll, queue, retry, resume, or complete it independently. The two V1-scope views take no action at all: they are read-only projections whose closed route set accepts exactly the methods `GET` and `HEAD`, carries no request body, and lets no path, query value, or header select a filesystem path, a command, a stage, or a business mutation. Every other method, `OPTIONS` included, is refused under rule 7 without resolving a selector. A `HEAD` request performs the same resolution and revalidation as the `GET` it mirrors and returns that outcome's status and headers with an empty body, so rule 6's body-equality requirement binds `GET` alone; a request that declares a body is refused as malformed under rule 7's 400 outcome rather than read. Because those bytes are never drained, that refusal — and any earlier one, such as an unsafe method carrying a body — closes the connection, so no undrained byte can be framed as the next request.
3. **Mirror view.** The mirror view presents the §17 report for one explicitly selected current `AssessmentSnapshot` as local HTML, preserving §16.11 status gates, uncertainty, contradictions, and source/generated-voice boundaries. The URL carries that selection explicitly in one of exactly two closed forms: the assessment-view identity — `scope`, plus its target for a project scope — or one exact `AssessmentSnapshot.id`. There is no default selector, no omitted-selector fallback, and no latest-of-several rule: an identity selector resolves only to the unique current snapshot of exactly that view, and both zero and more than one resolution are fail-closed outcomes rather than a choice. V1 serves the `global` identity; a project-scope selector is refused as the deferred slice it is rather than silently widened. That HTML is exactly §17's `report.html` member: the view performs §13.14's complete current-output revalidation for the selected snapshot — rule 5's standard, not merely matching-manifest validation — and serves those published bytes. It never renders a second version of the same projection, never re-renders around a failed revalidation, and never renders a partial claim set to work around a gate; a missing, stale, or invalidated set is a fail-closed outcome that names the §14.9 export the owner must run. Interactive provenance drill-down from claim to signal to fact to evidence is a named later iteration and is not part of the first mirror view.
4. **JD-to-bullet-pack view.** The view accepts owner-pasted vacancy text, writes the exact validated bytes to one owner-only operation-owned temporary file inside the workspace, requires that file to pass §29.4, supplies its path to the existing §14.10 JD-add operation, and removes it on completion under §29.6; a validation or cleanup failure is an operational failure and reports any residual path. The remaining generation, verification, and export work delegates to the same §14.10 flow without adding another business persistence or model contract. A successful export is one outcome; a refusal required by §18 or a §16.11 gate is an equally first-class completed `blocked` outcome under §14.14, with its reason and findings shown rather than replaced by an error page. An operational failure remains an operational failure and may not be relabeled as a semantic refusal.
5. **Gap-question handoff.** The sole outbound question-of-the-day source is the gap-question view over the same explicitly selected set. Exp2Res, never the shell, performs §13.14's complete current-output revalidation — not merely matching-manifest validation — validates the closed companion schema of that set's `out/assessment/<snapshot-id>/self_claims.json` from §13.12–§13.14, projects only `unknowns` entries with `answered = false`, and presents only their `question` values — §17's open-question set. No other companion field, and no gap ID, target, reason, priority, claim, or contradiction, reaches the page, so a question stays readable without becoming an answer link-back token. The shell embeds one URL: it reads no companion file, manifest, or workspace path, inherits no companion schema, cannot bypass revalidation, and never constructs a path from the scope target. A stale historical set, a set invalidated by a later gap answer, or a cleanup residual is never a handoff source. Exp2Res receives no consumer identity or answer callback. An answer returns only through ordinary diary/activity capture or import as a new `RawLog`; it carries no gap ID or link-back token, and §14.7's no-relink rule remains unchanged.
6. **Closed route set and per-request revalidation.** The served routes are exactly `/mirror` and `/questions`, each carrying rule 3's selection as exactly one query selector — `scope`, or `snapshot`. When the deferred project scope is implemented, `scope=project` takes its target in exactly one additional `project` parameter carrying the §14.9 canonical project label, and that pair is the whole of the identity form; V1 recognizes the shape only to refuse it as deferred. Any other path, an absent, unknown, repeated, combined, or malformed selector, and any additional parameter are refused rather than interpreted. The only request headers any route consults are the ones those refusals need: the authority and declared origin rule 1 checks, a fetch-metadata site declaration when the client sends one, and the framing headers rule 2 reads to detect a declared body. Every other header is ignored — never interpreted, stored, or logged.

   Every request is its own read-only boundary: it re-reads §12.14 compatibility and performs its state reads inside one §8.1 read transaction, takes no workspace writer lock, and carries no cached bytes, resolution, or validation verdict between requests, so state that changed since the previous request is observed rather than served from memory. That read transaction is not free of effect and is therefore bounded: it opens when the request begins resolving and closes when the response is composed, before any byte reaches the socket, so a slow or idle client cannot extend a SQLite reader by even one byte's wait. Its duration is the server's own resolution and revalidation work and nothing else; §8.1's concurrent-reader outcome is unchanged, so a destructive checkpoint racing a request in flight may still report `deletion_incomplete`. It reads the revalidated member bytes once, so the bytes it serves are the bytes it verified. The mirror response body is exactly that revalidated `report.html` member; the gap-question response is one document generated under §17's HTML escaping, self-containment, and inertness rules over rule 5's projection alone. Beyond those two projections a response carries only rule 7's own outcome vocabulary — the outcome class, the §14 remedy command where one exists, and renderer-owned literal text — and a diagnostic line carries only the outcome class and, when the request named one, the closed route; neither ever carries request bytes, a workspace or managed path, `raw_text`, another companion field, or any other stored value. Every response is uncacheable and typed: each declares `Cache-Control: no-store` and the exact media type `text/html; charset=utf-8`, which a `HEAD` response carries too. So a revisited URL is resolved again by Exp2Res rather than replayed from an intermediate or browser cache, and no refusal is stored as a page. A document already delivered stays in the tab that rendered it, and Exp2Res controls that copy no more than it controls an opened §17 file member; what it guarantees is that the next navigation is a new request against current state. No page reflects request bytes back to its requester: a rule 7 remedy command names an `AssessmentSnapshot.id` only after resolution proved it is a current stored row, so what the page prints is state Exp2Res read, never a value a request supplied, and a refused, unresolved, or malformed selector reaches no page.
7. **Closed outcome set.** Every request completes in exactly one owner-visible outcome. Each names its outcome class, and names the §14 command that resolves it when one exists — the rows below whose remedy is a corrected request rather than a workspace operation name none, and none invents guidance to fill the space — and states nothing else about local state; a completed semantic refusal is never presented as an operational failure, and an operational failure is never relabeled as a refusal.

   A request that matches more than one row still has exactly one answer, because the checks are ordered and the first refusal decides it: transport parsing first, because a request line Exp2Res cannot parse carries no authority, method, or route to check; then rule 1's authority check, then the method, then rule 2's declared-body check, then the route, then selector parsing — all of it before any state is read — then §12.14 compatibility, then selector resolution, then §16.11's gate, and only then the managed set's revalidation. So a snapshot that both fails the allowlist and has had its stale set invalidated is the completed 403 refusal, never the 409 one: the export that row would name is exactly what the gate forbids.

   Each row's class value is the stable literal that names the outcome, and every response carries it in the `Exp2Res-View-Outcome` header — a service-owned constant, never a request value — so the class survives a bodyless `HEAD` and a `--quiet` invocation that suppresses §14.17's progress line. A refusal page states its class and remedy in the body as well; a served response states neither, because the mirror body is exactly the published `report.html` bytes and the question page is rule 5's projection alone.

   | Class | Outcome | Remedy command | Response status |
   |---|---|---|---:|
   | `served` | Revalidated content served. | — | 200 |
   | `malformed_request` | A request declaring a body, or a request line Exp2Res cannot parse. | none: correct the request | 400 |
   | `invalid_selector` | Absent, unknown, ambiguous, or malformed selector, or the deferred project-scope selector — named by `scope`, or reached through the ID of a project-scoped snapshot. | none: correct the request | 400 |
   | `assessment_blocked` | Completed semantic refusal: the selected snapshot fails §16.11's assessment-export allowlist. | the §14.9 verification for an unverified snapshot; for a completed negative verdict, the §14.9 generation that replaces the claims the verdict rejected, because reverifying unchanged claims reaches the same verdict | 403 |
   | `route_not_found` | A path outside the closed route set. | none: correct the request | 404 |
   | `no_current_view` | No current assessment view for the selected identity, or no current snapshot with the selected ID. | for an identity selector, the §14.9 generation; for an ID selector, only §14.14 rule 7's assessment listing, because no stored row names the view the requester meant | 404 |
   | `method_not_allowed` | Method other than rule 2's `GET` or `HEAD`; the response declares `Allow: GET, HEAD`. | none: correct the request | 405 |
   | `export_not_current` | Managed output missing, stale, invalidated, incomplete, or published under a superseded `manifest_version`. | the §14.9 export | 409 |
   | `schema_incompatible` | An incompatible or unrecognized §12.14 schema. | §14.1's migration only where §12.14 offers one — an older stored version with an available path; otherwise §14.1's read-only status inspection, because a newer stored version needs a newer build and an unrecognized one has no migration to run | 409 |
   | `authority_not_bound` | Request authority, or a declared origin, other than the bound loopback one under rule 1. | none: correct the request | 421 |
   | `internal_error` | Unexpected local failure, reported without detail. | none | 500 |
   | `workspace_busy` | §8.1 workspace contention: another command holds the workspace. | none: retry once that command finishes | 503 |

8. **Serving process boundary.** Serving performs no business mutation, no managed-output publication or reconciliation, no §12.13 `processing_runs` or §12.15 `llm_calls` row, and no §15 call, so a served page never authorizes what its underlying §14 flow would require. §14.17 owns the command form, its bind controls, and its §14.14 envelope; §8.1 classifies that command read-only and owns its per-request transaction discipline.

These views add no LLM transmission field, so §29.3 does not widen. They expose no source payload, result, or action beyond the selected §17 projection, the validated unknown-question projection, and the same §14 flows available without a view.
